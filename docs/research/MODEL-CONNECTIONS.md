**Domain:** How Warden's runner connects to model servers. Today the OpenCode adapter assumes LM Studio on loopback. The owner's direction is to connect simply through open, standard connections (the OpenAI-compatible API and the Anthropic Messages API) to any local or remote server, configured per environment, and to tune the MVP for mlx-serve (mlxserve.com), which now replaces LM Studio on the maintainer's Mac.

## Summary

Warden can stay provider-neutral with one rule: every model connection is an **environment record that names an API style, a base URL, a credential reference, an exact model id, limits and capabilities**. Warden renders that record into the harness config instead of assuming LM Studio. **OpenAI-compatible `/v1/chat/completions` plus `/v1/models` is the only pair every server examined supports**, so it should be the required floor. **Anthropic Messages (`/v1/messages`) is now widely available but always a translated subset**, so it should be a second path that Warden checks with live probes before using it. The owner is right that Ollama (v0.14.0 and later) and LM Studio (0.4.1 and later) speak both protocols. So do llama.cpp, vLLM, SGLang, self-hosted NVIDIA NIM and mlx-serve. `mlx_lm.server` and NVIDIA's hosted build.nvidia.com API document only the OpenAI side. For the MVP, mlx-serve (ddalcu/mlx-serve, the project behind mlxserve.com) fits Warden's OpenCode runner almost exactly: it documents the same `@ai-sdk/openai-compatible` setup Warden generates. But it breaks three things the shipped code assumes: the port (11234, not 1235), how the context window is found (`/v1/models` row fields, not LM Studio's `/api/v0`), and the idea that a loopback URL means inference ran on this Mac. mlx-serve, like LM Studio and Ollama, can proxy a request to another machine behind `localhost`. The main recommendation is to replace Warden's "local-only" claim with **"approved endpoints only"**. Under it, each run records which tier served it: a local model, the owner's large remote Nemotron/Gemma inference service, or a frontier model. Each tier claims only what Warden can enforce. Everything below is a proposal for the owner, not a decision already made.

## OpenAI chat completions is the floor; Anthropic Messages is a probed second path

All the servers in scope expose OpenAI-style chat completions, and `/v1/models` is close to universal. Beyond that pair, support splits quickly. **Anthropic `/v1/messages` arrived across the local-server field in January 2026.** Ollama added it in v0.14.0 on January 16 ([Ollama blog](https://ollama.com/blog/claude)). llama.cpp added it through PR #17570, announced January 19 ([HF blog](https://huggingface.co/blog/ggml-org/anthropic-messages-api-in-llamacpp)). LM Studio added it in 0.4.1 on January 30 ([LM Studio 0.4.1 changelog](https://lmstudio.ai/changelog/lmstudio-v0.4.1)). vLLM has it in its v0.11.1 docs ([vLLM v0.11.1 API docs](https://docs.vllm.ai/en/v0.11.1/api/vllm/entrypoints/anthropic/serving_messages/)). SGLang registers it on every server ([SGLang Anthropic API docs](https://docs.sglang.io/docs/basic_usage/anthropic_api)), and self-hosted NIM 3.0.0 lists it along with `count_tokens` ([NIM 3.0.0 API reference](https://docs.nvidia.com/nim/large-language-models/3.0.0/reference/api-reference.html)). The two gaps are `mlx_lm.server`, which documents only chat, completions, models and health ([DeepWiki mlx-lm](https://deepwiki.com/ml-explore/mlx-lm/3.3-http-server)), and NVIDIA's hosted per-model reference for Nemotron 3 Ultra, which shows only Bearer-authenticated `/chat/completions` at `integrate.api.nvidia.com` ([NVIDIA API reference](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-ultra-550b-a55b-infer.md)).

Sources for the table: [Ollama docs](https://docs.ollama.com/llms-full.txt), [Ollama Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility), [LM Studio API changelog](https://lmstudio.ai/docs/developer/api-changelog), [llama.cpp README mirror](https://huggingface.co/OpenTransformer/llama.cpp-prismml/blob/main/tools/server/README.md), [vLLM online serving](https://docs.vllm.ai/en/latest/serving/online_serving/), [mlx-serve api.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/api.md), [LiteLLM native passthrough](https://docs.litellm.ai/docs/anthropic_unified/native_passthrough), [LM Studio LM Link](https://lmstudio.ai/docs/developer/core/lmlink).

The Anthropic column needs a caveat: **every local implementation converts Messages onto its own chat-template and tool-parser pipeline.** vLLM's serving class is a set of `_convert_anthropic_to_openai_request` and `_convert_tool_*` methods ([vLLM v0.23.0 docs](https://docs.vllm.ai/en/v0.23.0/api/vllm/entrypoints/anthropic/serving/)). So Anthropic tool use works only where the server's OpenAI tool calling already works for that model. Feature coverage also varies a lot. Ollama ignores `tool_choice`, `metadata` and `cache_control`, accepts `budget_tokens` without enforcing it, and has no `count_tokens` ([Ollama Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility)). LM Studio's page documents little beyond basic messages, streaming and tools ([LM Studio Anthropic Messages](https://lmstudio.ai/docs/developer/anthropic-compat/messages)). SGLang returns `tool_use` blocks only when the operator sets `--tool-call-parser`; without it, tool calls come back as raw text ([SGLang docs](https://docs.sglang.io/docs/basic_usage/anthropic_api)). The practical result: **a provider-neutral client can require chat completions, but must earn the right to use Messages, tools or structured output on each endpoint by probing.** That matters most for the owner's remote Nemotron/Gemma service. If it runs on NIM, vLLM or SGLang, it can serve both protocols, but the operator has to pick the right tool parser for each model family. If it goes through NVIDIA's hosted API, only chat completions is documented, and even there `tools` and `tool_choice` appear in code samples but not in the formal request schema ([NVIDIA API reference](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-ultra-550b-a55b-infer.md)). Which of these the owner's service is remains unknown, and the answer decides its API style in the environment record.

## Follow the published specs, not each server

Researched 2026-11-25 after the owner asked to "research the apis and follow them". The rule this section proposes: **Warden sends only what the official spec defines, reads only what the official spec defines, and treats every server as a conforming or non-conforming implementation of that spec.** Server-specific fields (mlx-serve's `context_length`, LM Studio's `/api/v0`, Ollama's `/api/show`, `reasoning_content`) are not part of the design. Tuning the MVP for mlx-serve then means configuration values (base URL, model id, limits), not code paths.

### What the two specs actually are

| | OpenAI API | Anthropic Messages API |
|---|---|---|
| Canonical spec | OpenAPI 3.1 file, `info.version` 2.3.0, MIT, generated from OpenAI's internal source ([openai-openapi](https://raw.githubusercontent.com/openai/openai-openapi/main/openapi.yaml), fetched 2026-11-25; the file carries no date) | API reference on platform.claude.com ([Create a Message](https://platform.claude.com/docs/en/api/messages/create.md)); no public OpenAPI URL was found |
| Conformance definition for third parties | None for Chat Completions. **Open Responses**, a vendor-neutral spec based on the Responses API under LF Projects, has its own OpenAPI file and a compliance test tool; versions 2026-01-15 and 2026-04-24 ([openresponses.org](https://openresponses.org/), [InfoQ](https://www.infoq.com/news/2026/02/openai-open-responses)) | None. The nearest is Claude Code's gateway contract: `/v1/messages` with real streaming, `ping` passed through, error bodies unmodified; `count_tokens` and `/v1/models` optional ([gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol.md)) |
| Base URL and auth | `https://api.openai.com/v1`; `Authorization: Bearer` | `https://api.anthropic.com` (no `/v1`); `Authorization: Bearer` is now primary and `x-api-key` a legacy fallback; `anthropic-version` required ([overview](https://platform.claude.com/docs/en/api/overview.md)) |
| Versioning | None in headers | `anthropic-version`: `2023-06-01` still listed; `2026-10-21` is newest and removes `temperature`, `top_p`, `top_k` ([versioning](https://platform.claude.com/docs/en/api/versioning.md), [migration](https://platform.claude.com/docs/en/api/migration-2026-10-21.md)). A client that sends no sampling parameters is valid under both |
| Model listing | `GET /v1/models`: only `id`, `object`, `created`, `owned_by` (plus optional `shutdown_date`). **No context window, output limit or capabilities anywhere in the spec** | `GET /v1/models/{id}`: `max_input_tokens` (context window), `max_tokens` (output cap), a `capabilities` tree, lifecycle fields; added since March 2026 ([models](https://platform.claude.com/docs/en/api/models/retrieve.md)) |
| Request floor | `model` and `messages` required; roles `developer`, `system`, `user`, `assistant`, `tool`; `max_completion_tokens` (with `max_tokens` deprecated); `tools`, `tool_choice` (`none`, `auto`, `required`, named); `response_format` `json_schema` with `strict` | `model`, `max_tokens`, `messages` required; top-level `system`; `tools`, `tool_choice` (`auto`, `any`, `tool`, `none`); structured output in `output_config.format` (`json_schema`), with `output_format` deprecated |
| Reasoning | No reasoning-text field in Chat Completions; only `usage.completion_tokens_details.reasoning_tokens`. `reasoning_content` is DeepSeek's extension ([DeepSeek](https://api-docs.deepseek.com/guides/reasoning_model)). The Responses API has official reasoning items | `thinking` content blocks with `signature`; parameter modes vary by model |
| Streaming | SSE `chat.completion.chunk`, ends with `data: [DONE]`; usage in a final chunk only with `stream_options.include_usage`; an error object may arrive mid-stream | SSE `message_start` → block start/delta/stop → `message_delta` → `message_stop`; `ping` anywhere; `error` event possible after HTTP 200; unknown event types must be tolerated ([streaming](https://platform.claude.com/docs/en/build-with-claude/streaming.md)) |
| Errors | `{error:{message,type,param,code}}`; 429/503 may carry `Retry-After` | `{type:"error",error:{type,message},request_id}`; status-to-type table including 529 `overloaded_error` ([errors](https://platform.claude.com/docs/en/api/errors.md)) |

### What following the specs changes in this note

1. **Context window and output limit come from the endpoint record, or from a spec field, never from vendor fields.** On the OpenAI path the spec defines no such field, so `limit.context` and `limit.output` become **required** values in each endpoint entry (for the MVP, the owner copies them from mlx-serve's load settings once). On the Anthropic path Warden may read `max_input_tokens` and `max_tokens` from `GET /v1/models/{id}` when the server implements it, and must otherwise require the configured values. If the window is unknown, the run refuses; it never falls back to a guess (today's 131072 fallback) and never silently turns the window guard off.
2. **Preflight becomes a spec-conformance check.** It lists models with `GET /v1/models` (spec fields only, no redirects), sends one minimal spec-shaped request in the endpoint's declared style, and checks the response against the spec schema (required fields, `finish_reason` or `stop_reason` in the spec's enum, usage present). For sessions that use tools, one forced tool call must come back as a structured `tool_calls` entry or `tool_use` block. A server that fails is reported as non-conforming for that endpoint; Warden does not add a workaround for it.
3. **Requests carry only spec fields.** No `reasoning_content`, no vendor body fields, no `@peer` ids treated as special. Warden's own HTTP calls branch on HTTP status, not on the error `type` string (the two specs, and Open Responses, name types differently).
4. **The harness must speak the spec too.** Warden's model traffic goes through OpenCode, so following the spec means choosing OpenCode's standard OpenAI-compatible and Anthropic-compatible provider packages, rendering only spec-level settings (base URL, key, model id, limits), and pinning a version whose requests were checked against the spec. The OpenCode reasoning-field fix in 2.3.1 (it stopped replaying `reasoning_details` to `reasoning_content` models) is a sign that the harness can itself emit non-spec fields; the preflight should record the wire request once per pinned version.
5. **Locality is not a spec question.** Neither spec says where a model runs, so the data-boundary tiers and enforced egress in the section on loopback still apply unchanged.

### Choices the specs leave open

- **OpenAI side: Chat Completions or Open Responses.** Chat Completions is what every server examined serves and what OpenCode's OpenAI-compatible package uses, but it has no conformance suite. Open Responses is a formal open spec with a compliance tool, and mlx-serve, Ollama (stateless only), LM Studio, llama.cpp, vLLM and NIM serve `/v1/responses`; a headless client must send `store: false` because the official API defaults to storing for at least 30 days. Recommendation: Chat Completions for the MVP, Open Responses as the conformance target to move to once OpenCode and the pilot servers pass its compliance tool.
- **Anthropic side: which `anthropic-version`.** Recommendation: send `2023-06-01`, which the local servers implement and Claude Code still sends, and never send sampling parameters, so the same request is valid under `2026-10-21` as well.

## mlx-serve covers the runner's needs but breaks three shipped assumptions

mlx-serve is an MIT-licensed, Zig-native server with a Swift menu-bar app for Apple Silicon. It is **not a wrapper around `mlx_lm.server`**: it calls MLX through `mlx-c` and embeds llama.cpp for GGUF ([mlxserve.com](https://mlxserve.com/); [repo](https://github.com/ddalcu/mlx-serve)). Two unrelated projects carry nearly the same name: the PyPI package `mlx-serve` by raspoli ([PyPI](https://pypi.org/project/mlx-serve/)) and `mlx_lm.server`. Warden's docs should therefore name it **"mlx-serve (ddalcu)"**. Its API surface is a superset of what Warden's OpenCode runner uses. OpenAI chat completions, completions, Responses, embeddings and models, plus Anthropic Messages and Ollama's `/api/*`, all share one port ([api.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/api.md)). Its integration guide documents an OpenCode provider that is **`@ai-sdk/openai-compatible` at `http://127.0.0.1:11234/v1` with `limit.context` taken from `/v1/models`**, which is the shape Warden already generates ([integrations.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/integrations.md)).

| What Warden's runner and preflight need | What the shipped code does | What mlx-serve exposes |

| Model listed | `GET {base}/models`, exact `id` match (opencode.ts:129) | `/v1/models` lists "loaded models with capabilities + engine info"; the id is the directory basename or an alias ([CHANGELOG](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/CHANGELOG.md)) |

Three of these rows need code changes. The **context-window step fails against mlx-serve**. The `/api/v0` request returns 404, Warden keeps 131072, and the window guard is then disabled (`ctxKnown` false, opencode.ts:55). That guess is dangerous, because mlx-serve "pins the real window at model load (memory-bounded, often well under the model max)". Its docs warn that hardcoding a bigger number "means overflows" ([integrations.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/integrations.md)). *(Superseded by the spec-following rule above: these are mlx-serve and vLLM extras, not spec fields, so Warden should not depend on them; the window becomes a required endpoint value.)* The earlier proposal was to read the window from the `/v1/models` row Warden already matched, in the order top-level `context_length`, then `max_model_len`, then `meta.context_length`. `max_model_len` is also the vLLM convention. That convention comes from background knowledge, not a doc read in this research, so it needs a live check. Because mlx-serve loads models on demand, keeps up to 3 resident by default and evicts the least recently used ([cli.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/cli.md)), a listed model is not necessarily resident. The safest sequence is to send one tiny warm-up request, then re-read the row.

The **bind default** is a real hazard. mlx-serve's own pages contradict each other. `docs/cli.md` says the default is `--host 0.0.0.0`, and v26.8.4 added a warning that the server is reachable from the network. SECURITY.md and the homepage say the default is 127.0.0.1 ([SECURITY.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/SECURITY.md)). Whether the Mac app's embedded server binds to all interfaces is unconfirmed. Warden's runbook should require `--host 127.0.0.1` and check the listener with `lsof`, not trust either page. The **remote-model suffix** is the third break: the only documented marker that a model is remote is an `@` in its id, and no documented `/v1/models` field says "remote". Finally, the project moves fast. The CHANGELOG reaches v26.11.4, while the GitHub Releases page still showed v26.9.2 as "Latest" ([Releases](https://github.com/ddalcu/mlx-serve/releases)), and fixes to tool-call parsing land almost every release. So **Warden should record the mlx-serve version each run used**, not assume a version.

The owner said mlx-serve "has access to higher models and is better managing memory". The notes cannot tell which feature he means. Candidates are SSD expert streaming for large MoE models on 128 GB Macs, two-Mac RDMA over Thunderbolt 5 ([README](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/README.md)), the `--max-resident-mem` and idle-eviction controls, or the Providers feature, which fronts any OpenAI-compatible server through the same URL. The difference matters. The first three keep inference on hardware the owner controls. Providers can quietly route a "local" URL to the remote Nemotron/Gemma service or a frontier API.

## One environment record, rendered into OpenCode, settles most of the neutrality question

The harness and client survey shows that tools converge on the same minimal record. That record has an API style, base URL, credential as an environment-variable reference, wire model id kept apart from the local alias, context window, max output tokens, capability flags, and an escape hatch for extra headers or body fields. pi's `models.json` is the most explicit version, with `api` values such as `openai-completions`, `openai-responses` and `anthropic-messages`, and defaults of 128000 context and 16384 output ([pi models-configuration](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/models-configuration.md)). OpenCode 2.x has the same parts. A provider has `package`, `settings.baseURL`, `env`, `headers`, `body` and `compatibility`, and a model has `modelID`, `limit` and `capabilities` ([OpenCode providers](https://opencode.ai/docs/providers.md)). The proposal is a **`runtime.endpoints` registry in Warden config, with one entry per environment**, rendered into `opencode.json`. Warden would choose OpenCode's openai-compatible or anthropic-compatible package from the entry's API style, write `capabilities` explicitly rather than trust discovery (OpenCode's vLLM discovery starts tools disabled ([providers.md](https://opencode.ai/docs/providers.md))), and use the entry id as the provider id instead of the hardcoded `lmstudio`.

Two OpenCode details need hands-on verification before coding. First, the v1-to-v2 migration guide rewrites `"npm": "@ai-sdk/openai-compatible"` as **`"package": "aisdk:@ai-sdk/openai-compatible"`**. Current docs also name native `@opencode/ai/providers/openai-compatible` and `@opencode/ai/providers/anthropic-compatible` packages ([Migrate from V1](https://opencode.ai/docs/migrate-v1/)). Warden's generated config uses the bare `@ai-sdk/openai-compatible` (opencode.ts:69). It works in the shipped proofs, but whether 2.2.7 treats it as an npm install or an alias is undocumented. Second, the pinned 2.2.7 predates two fixes that bear directly on mixed endpoints. 2.3.0 lets providers present a client certificate through `settings.tls`, and 2.3.1 stops sending `reasoning_details` to models that use `reasoning_content` and fixes mid-session model switches on OpenAI-compatible providers ([OpenCode changelog](https://opencode.ai/changelog.md)). If Warden upgrades past 2.4.0, the model and provider lists can be "empty or partial" right after startup, so preflight must poll or wait for `model.updated`.

*(Superseded in part by the spec-following rule: vendor probes are dropped; only explicit config and spec fields remain.)* Discovery should follow a fixed precedence: explicit environment config first; then the standard `/v1/models` row fields; then server-specific probes only when the server type is declared (LM Studio `/api/v0` or `/api/v1`, Ollama `/api/show`, llama.cpp `/props`); then conservative defaults. Warden should log which source supplied each value. Preflight should grow from today's "listed and loopback" check to a four-step probe. Step one lists models without following redirects; Claude Code treats any redirect as failure ([Claude Code gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol.md)). Step two sends a tiny completion in the configured API style and asserts the response's `model`, finish reason and usage. Step three, for repo-context sessions, forces one trivial tool call and asserts a structured call came back, not JSON inside the text. Step four, optionally, finds which field carries reasoning. LiteLLM's health check supports a larger probe budget, noting that "Reasoning models often need more headroom" ([LiteLLM health](https://docs.litellm.ai/docs/proxy/health)). Its `mode: anthropic_messages` shows the same probe can target the Messages path.

Several pitfalls are already documented and apply here. The base-URL convention flips by API style: OpenAI-style bases include `/v1`, while Ollama's and LM Studio's Anthropic bases omit it ([Ollama Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility); [LM Studio Anthropic compat](https://lmstudio.ai/docs/developer/anthropic-compat)). OpenCode turns an unset `{env:VAR}` into an empty string, so a missing secret shows up only as a 401 at run time ([OpenCode config](https://opencode.ai/docs/config/)). Warden should check required variables itself. `llama-server` and `mlx_lm.server` both default to port 8080 ([llama.cpp README mirror](https://huggingface.co/OpenTransformer/llama.cpp-prismml/blob/main/tools/server/README.md); [DeepWiki mlx-lm](https://deepwiki.com/ml-explore/mlx-lm/3.3-http-server)), so a port never identifies a server. Model ids are server-defined: mlx-serve accepts `org/repo` ids in requests but lists basenames, so Warden's exact-match check should be configured with the listed id or an alias. Claude Code, as a reference client, sends `thinking: {"type":"adaptive"}` to model names it doesn't recognise, which causes a 400 on upstreams that don't accept it ([Claude Code gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol.md)). Warden's own Anthropic path should send only fields its probes confirmed. pi's compat flags are effectively a catalogue of OpenAI-compatible divergences, and a small subset is worth carrying as per-endpoint overrides: `maxTokensField`, `supportsDeveloperRole`, `supportsUsageInStreaming`, `requiresToolResultName` and `thinkingFormat`. pi's own advice is not to enable features "based only on an endpoint advertising OpenAI or Anthropic compatibility" ([pi models.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/models.md)).

## A loopback URL proves the first hop, not where inference ran

Warden's shipped "local" guarantee rests on a loopback-literal check, a check that every enabled and resolved OpenCode provider is loopback, and a Seatbelt rule that limits the harness to one loopback port. ADR 0006 line 32 also promises an `lms ps` device equals `Local` check, but **that check never shipped in the runner** (it exists only in `proof/p0-runtime`). All three candidate local servers defeat a pure loopback test. LM Studio's LM Link docs say "Requests to `localhost` still work as normal" while the model runs on a linked remote device ([LM Studio LM Link](https://lmstudio.ai/docs/developer/core/lmlink)). Ollama's cloud models run on "Ollama's cloud service" through the same local API ([Ollama cloud](https://docs.ollama.com/cloud)). mlx-serve's FAQ says a peer's shared model lets "even Claude Code pointed at `localhost`" run on another Mac ([faq.md](https://raw.githubusercontent.com/ddalcu/mlx-serve/main/docs/faq.md)). None of the three documents a reliable per-response field saying where a request ran. **Any proof that does not trust the vendor has to come from enforcement, not metadata.**

Evidence can be ranked from weakest to strongest. Server-declared signals are weakest. Examples are LM Studio's `device`, Ollama's `Ollama cloud disabled: true` log line after `OLLAMA_NO_CLOUD=1` ([Ollama FAQ](https://docs.ollama.com/faq)), mlx-serve's `@` suffix, and LiteLLM's `x-litellm-model-api-base` header ([LiteLLM OWASP mapping](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10)). These are worth recording but self-reported. Port ownership comes next: `lsof` gives the listener's PID, and `codesign` gives its Team ID. That proves which program answers, not where it forwards. A point-in-time egress snapshot of that PID catches long-lived tunnels and misses short ones. **Enforced egress on the server process** is the only rung that does not trust the vendor. Either the server runs under a profile that allows only loopback, or a per-process firewall such as LuLu, which has a block mode with an allow list, denies the server binary all non-loopback outbound traffic ([Objective-See LuLu](https://objective-see.org/products/lulu.html)). Two costs come with that. Apple's DTS staff say `sandbox-exec` is deprecated and its profile language "is not documented for third-party use" ([Apple Developer Forums](https://developer.apple.com/forums/thread/661939)), so Seatbelt is defence in depth, not a long-term foundation. And denying egress breaks mlx-serve's self-update and model downloads, so a "maintenance" mode and a "serving" mode would have to alternate, with Warden checking which one is in force.

That supports an honest tier vocabulary in place of the binary local/remote flag. **`local-enforced`** means loopback, a verified listener binary and denied server egress; only this tier may say "stayed on this Mac". **`local-unverified`** means loopback without enforcement; Warden reports the server's own metadata but must not call it local. **`self-hosted-remote`** fits the owner's large Nemotron/Gemma service: HTTPS to an exact registered hostname, with an SPKI pin or mTLS where the operator can provide one. *(For the owner's service, ruled 2026-11-25: no pin or mTLS; see Owner rulings.)* **`vendor-remote` or `frontier`** covers third-party APIs governed by contract and retention terms. **`attested-remote`** stays optional for later. GPU confidential computing costs only about 1 to 7.5 percent of throughput on Blackwell ([NVIDIA Technical Blog](https://developer.nvidia.com/blog/hardware-rooted-ai-security-that-wont-slow-you-down/)). It needs a TDX or SEV-SNP confidential VM, though, and the client-side pattern, where data is sent only when the TLS key matches the attested key, comes from vendors like Tinfoil ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)). Self-hosting that is not realistic for the MVP.

The registry should be deny-by-default, the reverse of LiteLLM, where "Access is open until a list is defined" ([LiteLLM OWASP mapping](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10)). Each entry would carry a tier, transport rule, expected identity, exact model ids with no wildcards, protocol, the highest repository classification it may receive, a consent requirement and a budget. Hosts would be compared after canonicalisation and exactly, the way `classifyBaseURL` already rejects userinfo and lookalike hosts. Automatic redirects would be off. For remote tiers, the cleanest design keeps Seatbelt's single-loopback-port rule intact. **All harness traffic goes to one Warden-owned loopback forwarder.** The forwarder holds the registry, pins TLS or presents the mTLS certificate, counts bytes, writes the audit record and refuses unknown hosts. This is a design proposal, not a cited pattern. It also means a remote tier never needs to widen the harness sandbox. Two rules close the loop. **No silent fallback**: a failed endpoint stops the run, and moving to another tier needs fresh consent. **Verdict provenance**: every review and auto-merge verdict records the tier, endpoint and model that produced it. That fits the owner's correction that Warden's auto-merge verdict does not rest on local models. The record states whether a verdict came from a local model, the remote Nemotron/Gemma service or a frontier model, so nothing implies the gate is local-only.

## Conclusion

The neutrality problem turned out to be mostly a configuration and honesty problem, not a protocol problem. The open protocols already exist on nearly every server, including the one the owner just switched to. What tied Warden to one host was three LM Studio-specific details hardcoded in one file: a port, a `/api/v0` metadata call and a provider id. Replacing them with an endpoint record and standard `/v1/models` fields makes mlx-serve, Ollama, vLLM, NIM and a frontier API interchangeable at the wire level.

The deeper finding is that the old "local-only" guarantee was weaker than it read, even before mlx-serve. Every popular Mac server can tunnel a "localhost" request elsewhere, and the device check that was meant to catch it never shipped. Moving to "approved endpoints only" with named tiers is therefore not a loosening of Warden's privacy stance. It is the first version of the claim that Warden can actually prove. It also lets Warden say plainly which model, local or remote, stood behind each gate decision. The open questions left are empirical and cheap to settle with a live probe on the owner's Mac: the exact `/v1/models` JSON mlx-serve returns, the Mac app's bind address, whether Providers models appear over HTTP, and how OpenCode 2.2.7 resolves the package string.
