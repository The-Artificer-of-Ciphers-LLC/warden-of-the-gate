# Feature Research

**Domain:** AI-assisted GitHub repository maintenance (issue triage, PR review, auto-fix PRs, stale management). Delivered as a local, batch-run Claude Code plugin for one maintainer. The maintainer stays in the loop and the plugin never merges.
**Researched:** 2026-11-10
**Confidence:** MEDIUM overall. The categorisation is a judgment grounded in PROJECT.md, the PRD and the ADRs. Facts about other products come from official vendor docs and changelogs, but the confidence seam rates all web-sourced claims LOW. The claims that would change a design decision are marked "verify" and should be re-checked in the phase that relies on them.

## Comparable Products Surveyed

| Product | Category | What it teaches Warden |
|---------|----------|------------------------|
| `actions/stale` | Stale bookkeeping (Action) | Sets the baseline that is expected: per-type clocks, exempt labels, exempt drafts, `operations-per-run` cap that resumes next run, `debug-only` dry run. The weakness is that any update counts as activity, bot comments included, and there is no notion of whose turn it is. |
| Kubernetes Prow + triage robot | Large-OSS lifecycle | `needs-triage` is required until `/triage accepted`. Lifecycle runs stale (90d), then rotten (+30d), then closed (+30d), with `/lifecycle frozen` and `/remove-lifecycle`. A 2022 proposal stopped staling triaged issues. `/hold` exists. Labels serve as the state machine. |
| VS Code triage actions | Large-OSS triage | `needs more info` closes after 7 days only when the last interaction came from a team member. This is the "ball is in the reporter's court" rule. |
| Probot no-response / request-info / welcome | Lightweight bots | `responseRequiredLabel` plus `daysUntilClose` (commonly 14). These apps are archived in favour of Actions, so bots without state and without AI have become a commodity. |
| rustbot / slash-assign / take actions | Claim mechanics | `@rustbot claim` / `release-assignment`. For users outside the org, rustbot assigns itself and records the claimant in the issue body. Slash-assign style actions unassign after N days, with a pin label to exempt an assignment. |
| CodeRabbit | AI PR review (SaaS) | Incremental review of commits since the last review, plus `full review`, `pause`/`resume`, and auto-pause after 5 reviewed commits. "Learnings" come from replies. `path_instructions` lives in `.coderabbit.yaml`. `emit path instructions` opens a PR that adds learned rules, which is close to Warden's Retro. |
| Copilot code review | AI PR review (GitHub-native) | Leaves a COMMENT review by default and does not count toward approvals. Re-review on push is off unless "Review new pushes" is set. The docs say it may repeat comments you resolved or downvoted. It reads instruction files (including `REVIEW.md`) from the head branch, so a fork can rewrite its own review rules. |
| Copilot coding agent | Issue-to-PR agent | Opens a draft PR and cannot mark it ready, approve, or merge. Iteration happens through PR comments. |
| Sweep AI | Issue-to-PR agent | Deprecated its GitHub issue-to-PR bot and pivoted to an IDE plugin. Unattended issue-to-PR at volume did not hold up as a product. Throttles and human gates are required, not optional. |
| Claude Code Review (Anthropic) | AI PR review | Specialist agents, then a verification step that checks each candidate against real code behaviour. Findings carry a severity. The check run is always neutral and never blocks. It reads `REVIEW.md` / `CLAUDE.md`. |
| GitHub Agentic Workflows (gh-aw) | AI in Actions | "Safe outputs": the agent is read-only and a separate job with permissions performs writes, with per-type caps (1 comment, 1 PR by default). It has a staged/preview mode and a "Generated by..." footer. This is the closest architectural analogue to Warden's "headless writes a file, script posts". |
| Dependabot | Throttled bot PRs | `open-pull-requests-limit` (default 5), grouping, and comment commands (`rebase`, `ignore`). Teaches the maintainer to expect a cap on concurrent bot PRs. |
| Mergify | Rules-based PR automation | Conditions-to-actions rules in a YAML file, merge queue, backports, and a report of which rules apply. Configuration as code is the norm. Warden must not drift into a merge queue. |
| GitHub native duplicate detection | Issue intake | Public preview since June 2026. Suggests up to 3 matches inline while the issue is being written. It only suggests and never closes. |
| Uber uReview | Internal AI review at scale | A second-pass confidence filter, with thresholds per category. Measures "addressed" rate (about 65%) and "useful" rate (75%). Precision beats recall. |

## Feature Landscape

### Table Stakes (Users Expect These)

Missing any of these makes the tool feel broken or unsafe. "Users" means the maintainer, contributors, and adopting maintainers.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **Config-as-code per repo** (`.github/warden.yml`, schema-validated, defaults merged) | Every comparable tool works this way: `.coderabbit.yaml`, `dependabot.yml`, `.mergify.yml`, stale workflow inputs. Adopters will not edit plugin source. | MEDIUM | Publish a JSON Schema so editors can autocomplete. Fail closed on an invalid config: the runner refuses to start and the workflows no-op with a clear message. Carry `schemaVersion` from day one. |
| **Dry-run / preview mode for every writing task** | `actions/stale debug-only` and gh-aw staged mode set this expectation. Nobody turns on an auto-closer without seeing what it would close. | LOW-MEDIUM | Implement once, in the poster script: "compute actions, then print instead of post". Sweep (Actions) needs it as much as review does. This is the general case of shadow mode. |
| **Global kill switch plus per-item hold** | Prow `/hold`, CodeRabbit `pause`. A maintainer needs to stop everything now, or stop one PR. | LOW | Kill switch: a repo variable checked by every workflow and by the runner before each batch, and again before each item (cheap). Per-item: a `warden:hold` label (name configurable) that every task skips. |
| **Explicit state labels (one per item)** | Prow and VS Code both use labels as the visible state machine. Maintainers already filter by labels. | MEDIUM | "Exactly one" needs an invariant checker. Sweep should detect items with 0 or 2+ state labels and report them, not guess. Creating labels belongs to `/warden setup`. |
| **Stale handling with exemptions** (drafts, `keep-open`, confirmed/approved, waiting on maintainer) | `actions/stale` already offers exempt labels and drafts, and Kubernetes exempts triaged issues. A stale bot without exemptions is one people come to hate. | MEDIUM | `actions/stale` exempts by label, not by whose turn it is. Warden's version must compute "waiting on whom". Read that from the timeline, not from `updated_at`. |
| **Throttles and caps** (items per batch, ops per run, open bot PRs, implements per day) | Dependabot `open-pull-requests-limit`, `actions/stale operations-per-run`, gh-aw per-output caps. Unbounded bot output is the top complaint. | LOW | Caps live in config. The rule "one open bot PR at a time" is easiest to enforce by counting open PRs from the App's author login at Implement start. |
| **Resumable batches** (stop cleanly, next run resumes) | `actions/stale` resumes when it hits its ops cap. Warden runs on a laptop that sleeps. | MEDIUM | Resume state comes from GitHub (labels and ledger), never from local files. A local cache is fine, but it must be disposable. |
| **Comment-only reviews that never block or approve** | Copilot code review defaults to COMMENT. Claude Code Review's check is always neutral. Approving is the human's job. | LOW | Post via the App with `event: COMMENT` only. Hard-code this in the poster: no code path should be able to send `APPROVE` or `REQUEST_CHANGES`. |
| **No re-review of an unchanged head** | Copilot reviews once by default. CodeRabbit re-reviews only new commits. Re-reviewing the same SHA is the motivating failure in GSD Core today. | LOW | `head == lastReviewedSha` means skip. Check it before any AI session starts so it costs no tokens. |
| **Incremental (delta) review on new pushes** | CodeRabbit has offered this for years. "Review new pushes" exists in Copilot. Full re-reviews on every push are what contributors find noisy. | HIGH | The delta must be the change in the PR's own diff (an interdiff), not `git log lastReviewedSha..head`. After the contributor merges main into the branch, the commit range contains upstream changes the contributor did not write. After a force-push, `lastReviewedSha` may not be an ancestor of head. Compute `diff(merge-base, lastReviewed)` against `diff(merge-base', head)`. When `lastReviewedSha` is unreachable (a GitHub API compare 404, or the commit was garbage-collected), fall back to a full review and record why in the ledger. |
| **AI-assistance disclosure on every contributor-facing output** | 51% of OSS AI policies require disclosure (arXiv 2026 survey). gh-aw adds a "Generated by" footer by default. Contributors penalise undisclosed AI more than disclosed AI. | LOW | The ADR 0003 voice header covers this. The header must be added by the poster script, not written by the model, so it cannot be dropped or reworded. |
| **Issue template / required-field check at intake** | GitHub issue forms are native. VS Code and Kubernetes both bounce under-specified reports. | LOW | Intake is not AI, so parse the issue-form sections (`### Heading` blocks) for required fields. The comment should name the missing fields, not say "please follow the template". |
| **Specific, bounded nudges** | Probot no-response and VS Code needs-more-info set this expectation. A nudge must say what is needed and when the item closes. | LOW | The template should include the outstanding action ("2 open findings: F2, F4"), the close date, and how to get an exemption. Allow at most 2 nudges (48h, 72h per ADR 0002), then close. |
| **Close message with a reopen path** | Kubernetes `/reopen` and the VS Code close message both give one. A close with no way back is rude. | LOW | Credit the work. For defect PRs, say the branch may be continued with `Co-authored-by`. Use `state_reason: not_planned` for stale issue closes. |
| **Backlog report / metrics** (open count, median age, items per state, re-review count) | Maintainers adopt automation to see the backlog shrink. Stale tools print statistics. | MEDIUM | Sweep computes metrics without AI. Write them to the Actions job summary and to one pinned tracking issue that is edited in place. The Foundation rollout gate needs the A–F bucket report before anything acts. |
| **Starter config plus label bootstrap** (`/warden setup`) | Onboarding has to fit in an afternoon (the v1 done criterion). CodeRabbit and Mergify both ship a starter config. | MEDIUM | No AI. It must be idempotent: rerunning it should not duplicate labels or overwrite a customised config. It should detect an existing `stale.yml` and warn that it conflicts (see Conflicts). |

### Differentiators (Competitive Advantage)

These follow from the Core Value: every item has one known state on GitHub, no head is reviewed twice, and the maintainer sees only the decisions that are theirs. The value is in persistence and gating. Review quality alone is not the differentiator.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **Ledger comment with findings that persist across pushes** (one comment per PR, edited in place, hidden JSON block) | No surveyed tool keeps a durable, inspectable state per finding. Copilot's docs admit it may repeat resolved comments. CodeRabbit's state is inside the vendor. Warden's state lives on the PR, so any run, machine, or future maintainer can pick it up cold. | HIGH | Anchor each finding by a fingerprint of `file + enclosing symbol + normalised snippet hash`. Line numbers move on every push. Statuses: `open`, `fixed`, `wontfix`, `superseded`. Guard against contributors editing the hidden block: the App owns the comment, but sign or hash the JSON and re-derive it on a mismatch. GitHub caps a comment at 65,536 characters, so the ledger must stay compact. |
| **Re-check open findings on every push** (fixed/still-open per finding) | Contributors see "F2 fixed, F4 still open" instead of a fresh pile of comments. This turns review into a checklist that converges. | MEDIUM | Re-checks are scoped to the finding's anchor, so they are cheap. They feed rounds-to-merge and the "addressed rate" metric (Uber measures the same thing). |
| **Won't-fix that sticks unless the code changes** | Removes the most-hated AI-review behaviour: being nagged about something already dismissed. | MEDIUM | Depends on the fingerprint. Re-raise only when the anchored region's hash changes. The maintainer marks won't-fix by resolving the review thread or replying `wontfix` on the finding (GraphQL `isResolved`; verify the field during the Review phase). Do not require the maintainer to edit the hidden JSON. |
| **Decision card at `pr:human-gate`** (linked issue, Merge Danger, CI evidence, open findings, recommendation) | No surveyed product hands the human a short merge decision. Mergify and Prow show status, not a recommendation. This is the "maintainer minutes per PR go down" metric made real. | MEDIUM | Put the card at the top of the ledger comment so there is only one place to look, and also list it in a local `/warden` digest of the decisions waiting. Keep it under about 15 lines. Recommendation values: `merge`, `merge after nit`, `request changes`, `close`. The card shows only the maintainer-only decision. |
| **Rules read from the base branch only** | Copilot reads instruction files from the head branch, so a fork PR can rewrite its own review rules. Reading from base closes a prompt-injection path. | LOW | Fetch `REVIEW.md`, specialists and tier paths with `gh api repos/.../contents?ref=<base>`. Never read rule files from the PR checkout. |
| **Risk-tiered review** (tier from paths and diff size: skip / light / full) | CodeRabbit has path instructions but no cost tiers. Tiering spends the limited Claude Code session budget where risk is. | MEDIUM | Tiering is deterministic (a script, config `tier paths`). Memtrace `get_impact` runs only on the full tier, and is optional. Show the tier on the decision card. |
| **Deterministic gates before AI** (CI status, conflicts, template, size, lint) | Avoids spending AI review on a PR that fails CI or has merge conflicts. | LOW | Run them in the runner before starting a session. A red CI produces a short "fix CI first" comment with no AI review. Count this in metrics as "gated, not reviewed". |
| **Verifier pass that filters findings before posting** | Claude Code Review and Uber both show that a second pass checking each finding against the code is what keeps noise down. Noise is the main reason AI review gets switched off (vendor reports of 60–90% of comments ignored). | MEDIUM | The verifier drops findings it cannot confirm against the code. Set a hard cap on blocking findings per review (for example 5) and route nits to a collapsed section or drop them. |
| **One consolidated review per round** (not a spray of inline comments) | Each inline comment notifies. Thirty comments a round is the noise pattern contributors complain about. | LOW-MEDIUM | Post one COMMENT review with a small number of inline anchors (blocking only) and a body that lists F-numbers. The ledger links to it. |
| **Author-turn-aware stale clock** (activity = author push, comment or review reply; bot comments and CI don't count; never stale while waiting on the maintainer) | `actions/stale` resets on any update, so a bot nudge resets its own clock. Research on stale bots found faster backlog closure but a large drop in active contributors. A clock that only runs while the contributor owes something keeps the benefit with less of that cost. | MEDIUM | Compute "whose turn" from the timeline: the last maintainer or Warden review or request, compared with the author's last push or comment. Unanswered PRs go to the review queue, not the stale path. One shared clock config feeds both Sweep and the docs (ADR 0002). |
| **Claim window for reporters who offered a fix** | rustbot and slash-assign offer manual claim and release. Granting the claim automatically based on the reporter's offer, with expiry, is rare. It protects contributor goodwill without blocking the queue. | MEDIUM | Track the claim in a label plus a ledger or issue comment, not through GitHub assignment alone. Assigning users outside the org has limits: rustbot works around it by recording the claimant in the issue body (verify GitHub's current rule for assigning commenters). On expiry, post a polite note and move to `ready-for-agent`. Treat a linked PR from the claimant as activity. |
| **Continuation credit on abandoned defect PRs** (`Co-authored-by`, continue from the author's branch) | Contributors' partial work is honoured, not discarded. Uncommon in other tools. | MEDIUM | Implement must branch from the contributor's head commit (fetch it read-only; never push to their branch), then build on it. This is the one place a fork's code gets checked out, so it conflicts with "never check out fork code" (see Conflicts). |
| **Shadow mode with agreement scoring** | gh-aw staged mode previews output, but nobody measures agreement. Warden's rollout gate (7 in 10 blocking findings agreed) turns shadow mode into a trust ramp backed by evidence. | MEDIUM | Shadow writes a local report with one row per finding and a place for the maintainer's agree/disagree. The agreement metric needs that capture step to exist. In shadow mode, the ledger is still updated in a local mirror so that "zero re-reviews" is testable. |
| **Retro: maintainer comments become `REVIEW.md` rules, as a PR** | CodeRabbit's `emit path instructions` is the nearest equivalent, but its learnings live in an opaque vendor store and accept replies from anyone. Warden's rules are versioned, reviewable, and come from the maintainer only. | MEDIUM | Input is the maintainer's review comments only, never contributor replies (blocks injection like "ignore rule X"). Output is a PR that touches `REVIEW.md` or lint config, which is human-gated by definition. |
| **Merge Danger summary on bot PRs** | Copilot coding agent PRs say what changed, not how risky it is. A risk summary lets "merge after a quick look" happen. | LOW-MEDIUM | Generate from the diff stats, the tier, Memtrace `get_impact` when it is on, and test evidence (the failing-first test name and its before/after result). |
| **Failing-first test on every auto-fix** | Sweep-era bots shipped plausible-looking fixes with no proof. A red-then-green test is the evidence the maintainer needs to merge quickly. | MEDIUM | Record the red run output (truncated) in the PR body. If the test cannot be made to fail first, stop and send the issue back to triage. |
| **Bounded rework** (named findings only, 3 rounds max, then human gate) | Prevents the AI-fixes-AI-review loop from running forever. | LOW | The rounds counter lives in the ledger. Rework may only touch the files and lines tied to the named findings. Diffs outside that scope get flagged by the verifier. |
| **Maintainer voice header with consistent identity across AI and Actions** | Contributors see one voice ("AI-assisted review by @maintainer") whether a nudge came from Actions or a review came from a local session. | LOW | One App, with installation tokens in Actions and the private key locally. See the "[bot]" pitfall in Conflicts. |
| **Local runtime with no API key** | No surveyed AI tool runs on the maintainer's own subscription. This is the cost differentiator for OSS maintainers. | MEDIUM | The runner refuses to start if `ANTHROPIC_API_KEY` is set. The docs should state plainly that throughput depends on the machine being awake. |

### Anti-Features (Commonly Requested, Often Problematic)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| **Auto-merge / approve when clean** | "The bot already said it's fine." CodeRabbit can flip to Approve, and Copilot approvals are opt-in. | Removes the human merge gate, the project's core promise. A bot approval also corrupts the two-reviewer signal Decision 4 relies on. | A decision card recommending `merge`. The maintainer clicks. |
| **Auto-close duplicates** | Duplicates waste triage time. 30% of maintainers asked GitHub for duplicate detection. | LLM and text-similarity duplicate bots have been reported auto-closing valid issues at scale. A false close loses the reporter for good. | Intake posts "possibly related: #A, #B" as a suggestion, without AI. Triage may propose `duplicate`, but closing is the maintainer's call, or happens only after reporter silence on an explicit question. GitHub's native duplicate suggestion at creation time already handles the reporter side. |
| **Real-time `@warden` chat commands answered instantly** | CodeRabbit, Copilot and Prow respond in seconds. | Warden is batch-only (ADR 0004). An instant-looking command interface promises a latency the laptop cannot deliver. Each contributor command is also an injection surface. | Maintainer-only labels as commands (`warden:hold`, `warden:full-review`, `keep-open`), read by the next batch. Actions without AI may acknowledge with a reaction. Contributors' only lever is pushing code or replying. |
| **Learning from anyone's replies** | CodeRabbit learnings are seen as magic. | Contributors can teach the reviewer to ignore rules (prompt or social injection), and the learnings are not visible. | Retro takes maintainer comments only and outputs a reviewable PR to `REVIEW.md`. |
| **Walkthroughs, sequence diagrams, poems, change summaries on every PR** | CodeRabbit's walkthrough is popular in demos. | Noise. It doubles comment length and costs session budget. The maintainer needs a decision, not a recap. | The decision card plus a one-paragraph summary inside the ledger. |
| **Inline nit floods / style comments** | "Be thorough." | Style nits make up most of the noise behind vendor reports of 60–90% of comments ignored. They train contributors to ignore the bot, real findings included. | Deterministic lint covers style. Cap blocking findings, and drop nits or collapse them. Retro can promote recurring nits into lint rules. |
| **Full re-review on every push** | "Make sure nothing regressed." | Re-reviewing everything is the motivating failure. It wastes the session budget and re-raises findings that were already settled. | Delta review plus re-checking open findings. A maintainer-only `warden:full-review` label forces a full pass. |
| **Three-stage lifecycle (stale, rotten, closed) on long clocks** | Kubernetes does it. | 90+30+30 days suits a huge contributor base. For one maintainer, it lets the backlog rot while sending three notifications per item. | Two nudges and a close on short PR clocks. Issue clocks scale by state (14d / 28d). Confirmed and approved items never stale. |
| **Staling items waiting on the maintainer** | Simple `actions/stale` configs do this by default. | Punishes contributors for the maintainer's latency. This is the documented driver of contributor decline. | The author-turn-aware clock. Items waiting on the maintainer go to the review queue and show up in metrics as maintainer debt. |
| **Pushing fixes to contributor branches ("Fix with Copilot" style)** | Saves a round-trip. | Violates contributor ownership. Fork branches often disallow it, and it surprises the author. | Suggested-change blocks in the review. For abandoned defect PRs, a new Warden branch with `Co-authored-by`. |
| **AI steps in GitHub Actions / API-key mode "for reliability"** | Always-on, no laptop dependency. | The cost constraint (ADR 0004). It also puts an Anthropic secret where fork-triggered workflows can reach it. | Catch-up-on-wake scheduling, plus Actions bookkeeping without AI so the clocks keep running while the laptop sleeps. |
| **Auto-applying `enhancement-approved` / `wontfix`** | Triage feels incomplete otherwise. | These are product decisions that belong to the maintainer. | Triage proposes them on the decision card. Only `confirmed-bug` is self-applied after root-causing (ADR 0001). |
| **Hosted dashboard / multi-repo UI** | Mergify and CodeRabbit have dashboards. | Out of scope (local, one maintainer). It would also be a second source of truth competing with GitHub. | A pinned metrics issue, the Actions job summary, and a local `/warden status` digest. |
| **Auto-assign reviewers / round-robin (blunderbuss)** | Prow has it. | One maintainer, so there is nobody to rotate to. It only adds notifications. | None needed. The decision card queue is the assignment. |
| **Merge queue / backports** | Mergify's core feature. | Different job, and it leads toward merging. | Leave it to Mergify or GitHub merge queue if the maintainer wants one. |
| **Generic first-time-contributor welcome spam** | `actions/first-interaction` is popular. | Adds one more automated comment to every new PR. It does not change any outcome. | Optional at most. A first-review header line can note "first contribution, thanks". Defer. |
| **Claiming GitHub "assignee" as the only claim record** | It is the native mechanism. | Assignment for users outside the org has limits, and assignees go silently stale. | A claim label plus a timestamp in the ledger. Assignment is set when it is allowed, but not relied on. |

## Feature Dependencies

```
Config schema + defaults
    └──requires──> /warden setup (labels, starter config)
                       └──requires──> State labels (one per item) + invariant check
                                          └──requires──> Ledger comment (hidden JSON)
                                                             ├──requires──> No re-review of unchanged head
                                                             ├──requires──> Delta (interdiff) review
                                                             │                  └──requires──> Finding fingerprints
                                                             │                                     ├──requires──> Re-check open findings
                                                             │                                     └──requires──> Won't-fix stickiness
                                                             ├──requires──> Rounds counter ──> Bounded rework
                                                             └──requires──> Decision card at pr:human-gate

GitHub App identity ──requires──> Voice header (added by poster) ──requires──> every contributor-facing post
Poster script (dry-run capable) ──requires──> Shadow mode ──requires──> Agreement capture ──> Review-live gate
Maintainer feedback capture (thread resolve / reply) ──enables──> Won't-fix, Agreement metric, Retro

Author-activity / whose-turn computation
    ├──requires──> Nudges (48h/72h) ──> Stale close (5d)
    ├──requires──> Issue stale clocks (14d / 28d)
    └──requires──> Claim expiry

Intake (template + dup suggestions) ──> Triage (configured command) ──> confirmed-bug
    ──> Claim window ──> ready-for-agent ──> Implement (failing-first, Merge Danger, 1 open bot PR)
    ──> Review (bot PR) ──> Rework (≤3) ──> Decision card

Deterministic gates ──precede──> Risk tiering ──precede──> AI review ──precede──> Verifier pass
Base-branch rule loading ──required by──> Review, Rework, Retro
Kill switch + warden:hold ──checked by──> every task
Sweep metrics ──requires──> state labels + ledger (counts derive from them)
Retro ──requires──> live review history (needs weeks of maintainer comments)
```

### Dependency Notes

- **Everything requires the state labels and the ledger.** Build these in Foundation, together with the invariant checker. Every task reads them to decide whether to act. If they are wrong, re-reviews and double-nudges follow.
- **Won't-fix stickiness requires finding fingerprints, which require an interdiff delta.** If findings are anchored to line numbers or the delta is a raw commit range, won't-fix breaks on the first merge-from-main. This is the hardest part of Review. Spike it before Review in shadow.
- **Shadow mode requires agreement capture.** The rollout gate (≥7 in 10) cannot be measured without a way for the maintainer to mark each finding agree or disagree. Design the shadow report format and the capture step together.
- **Maintainer feedback capture feeds three features** (won't-fix, agreement metric, Retro). Define it once: resolving a thread or replying to a finding, read through GraphQL.
- **The whose-turn computation feeds three features** (nudges, stale close, claim expiry). Build one library function with timeline fixtures. Each Sweep sub-feature calls it.
- **The poster script is where the voice header, the COMMENT-only rule, dry-run, and throttles are enforced.** It should be the only code path that writes to GitHub, so these rules hold structurally rather than by prompt.
- **Retro requires weeks of live review.** It belongs last (rollout stage 6), and its gate depends on there being enough maintainer comments to learn from.

### Conflicts

- **`actions/stale` (existing `stale.yml`, 28+14d) conflicts with Sweep.** Two clocks send contributors mixed signals (ADR 0002). `/warden setup` must detect it, and the migration docs must say to disable it.
- **Other AI reviewers (CodeRabbit, Copilot auto-review) on the same repo conflict with Review.** Contributors would get double reviews in different voices. Document "turn off other AI reviewers", or detect their reviews and say so on the decision card.
- **"Never call itself a bot" conflicts with GitHub App rendering.** GitHub shows App-authored comments as `<app-name>[bot]` with a bot badge (verify current rendering). Contributors will see "bot" in the author line whatever the voice header says. Name the App so that the `[bot]` suffix reads well (for example `trek-e-warden`), and keep the header wording honest. The "never calls itself a bot" rule can only cover the text Warden writes.
- **"Continue from the author's branch" conflicts with "never check out fork code".** Building on an abandoned fork branch means checking out and running its tests locally. Resolve this explicitly in the Implement phase: either continuing requires the maintainer's label (a human gate), or continuation happens only after the code has been reviewed and the maintainer has engaged.
- **Ledger edits in place conflict with notifications.** Editing a comment does not notify anyone. That is good for the ledger, but when a contributor action is needed (new findings, nudge), Warden must post a new review or comment so the author is notified.

## MVP Definition

The owner's v1 covers all six rollout stages, so "MVP" here means the minimum each stage needs to pass its gate.

### Launch With (v1)

- [ ] Config schema, defaults, `/warden setup`, label bootstrap. Required for portability and the "second repo in an afternoon" criterion.
- [ ] State labels, ledger comment, invariant checker, kill switch, `warden:hold`. Everything else depends on these.
- [ ] Bucket report (A–F). The Foundation gate.
- [ ] Poster script with dry-run, voice header, COMMENT-only rule, throttles. Enforces safety structurally.
- [ ] Interdiff delta review, finding fingerprints, re-check open findings, won't-fix stickiness. The Core Value.
- [ ] Deterministic gates, risk tiering, verifier pass, capped blocking findings. Needed to pass the ≥7/10 agreement gate.
- [ ] Shadow mode with an agreement-capture report. The Review-shadow gate.
- [ ] Decision card at `pr:human-gate`. The Review-live gate (maintainer minutes go down).
- [ ] Whose-turn computation, nudges, stale closes, issue clocks, claim window and expiry, Sweep metrics. ADR 0002, and the open-PR-count metric.
- [ ] Intake: template check, duplicate suggestions without AI (suggest only). The Triage-stage input.
- [ ] Triage runner around the configured command, one issue per session. The Triage gate.
- [ ] Implement: failing-first test, Merge Danger, one open bot PR, one per day. The Implement gate.
- [ ] Rework, max 3 rounds. Required for bot PRs to converge.
- [ ] Retro: weekly `REVIEW.md` PR from maintainer comments. The Retro gate.

### Add After Validation (v1.x)

- [ ] Local `/warden status` digest of pending decision cards across PRs. Add once the queue of decisions is long enough that opening the ledgers one by one hurts.
- [ ] AI-assisted duplicate candidates in Triage, beyond the text-similarity suggestions at Intake. Add if the Intake suggestions miss too often.
- [ ] Continuation of abandoned defect PRs from the author's branch. Add once the fork-code conflict has an agreed gate.
- [ ] Size/risk labels visible to contributors. Add if contributors ask why review is slow.
- [ ] A first-contribution line in the review header.

### Future Consideration (v2+)

- [ ] Non-macOS schedulers (systemd timers, Windows Task Scheduler). v1 is launchd only.
- [ ] Multi-maintainer repos (several voice headers, routing decision cards). Out of the solo-maintainer scope.

## Competitor Feature Analysis

| Feature | CodeRabbit / Copilot review | actions/stale / Prow lifecycle | Warden approach |
|---------|-----------------------------|--------------------------------|-----------------|
| Incremental review | CodeRabbit: commits since last review. Copilot: opt-in "review new pushes", may repeat resolved comments. | n/a | Interdiff since `lastReviewedSha`, plus re-check of open findings. Skips an unchanged head before any AI runs. |
| Finding persistence | CodeRabbit: inside the vendor, bulk `resolve`. Copilot: none. | n/a | Ledger JSON on the PR. Per-finding status. Won't-fix sticks unless the anchored code changes. |
| Review rules source | CodeRabbit: `.coderabbit.yaml` + AGENTS.md. Copilot: head-branch instruction files. | n/a | Base branch only (`REVIEW.md`, specialists, tiers). |
| Human gate | Copilot/Claude Code Review: comment-only, neutral. CodeRabbit can approve. | Prow: `/lgtm` + `/approve` by humans. | Comment-only, always ends at `pr:human-gate` with a decision card. |
| Stale activity | n/a | Any update resets the clock (bot comments included). Prow 90/30/30. | Author activity only. Never stale while waiting on the maintainer. 48h/72h/5d for PRs. |
| Claims | n/a | rustbot `claim`/`release`; slash-assign auto-unassign after N days. | Automatic claim window for reporters who offered a fix, expiry, then `ready-for-agent`. |
| Duplicates | n/a | GitHub native: suggests at creation. Third-party AI bots: some auto-close. | Suggest only at Intake. Closing is the maintainer's decision. |
| Disclosure | gh-aw: "Generated by" footer. Copilot: bot identity. | Bot account names. | Maintainer voice header added by the poster. App name chosen so `[bot]` reads honestly. |
| Learning | CodeRabbit learnings from any reply; `emit path instructions` PR. | n/a | Retro from maintainer comments only, as a reviewable PR. |
| Dry run | gh-aw staged mode. | `actions/stale debug-only`. | Poster-level dry-run for every task, plus shadow mode with agreement scoring. |
| Throttles | Dependabot `open-pull-requests-limit`. gh-aw per-output caps. | `operations-per-run`. | Item caps per batch, turn limits, 1 open bot PR, 1 implement per day. |
| Cost model | SaaS seat or usage pricing (Copilot about $0.25–$10 per review by effort level). | Free (Actions). | The maintainer's own Claude Code session. No API key. Actions does bookkeeping without AI. |
